# Learned phenotype scoring

The `analysis.phenotypeScorer` YAML option selects the native phenotype compatibility method. Omit it for Exomiser's existing Phenodigm behaviour. `INDIGENA` requires an offline entity embedding TSV; `EMBEDPVP_TRANSD` requires a complete, offline TransD bundle and an explicit per-analysis case ID whose entity is in that bundle. The selected method requires a `hiPhivePrioritiser` or `phivePrioritiser` step; a job with no compatible step is rejected. `weightedVariants.phenotypeWeight` must be specified, including when the desired weight is zero. Neither selector reads per-patient score TSVs. Invalid or unavailable resources stop the analysis.

`caseId` identifies the offline TransD case representation and is separate from Exomiser's VCF proband sample name. Exomiser's parsed `Sample` retains the proband name and HPO IDs, but has no independent benchmark case ID. The TransD bundle currently records model and parameter provenance, not a case-to-HPO profile checksum. The parser therefore verifies that the configured case entity exists; it cannot prove that the entity was trained or fine-tuned from the HPO profile in the current sample. Both output formats write `CASE_ID`, `SAMPLE_PROBAND`, and `SAMPLE_HPO_IDS` so the frozen case/profile mapping can be checked before inference and during prediction audit. A VCF sample name such as a GIAB identifier should not be equated with the benchmark case ID by convention.

The native `hiPhivePrioritiser` and `phivePrioritiser` use the selected scorer in Exomiser's existing model evidence and gene/inheritance aggregation. INDIGENA replaces the per-model phenotype similarity with embedding BMA. This native path keeps database model membership and its max-over-models behaviour; its `TSV_VARIANT` ranks are inherited gene ranks. Learned compatibility retains explicit zero-scored database models as evidence, so a lowest scaled TransD gene or an unscoreable INDIGENA model is not mistaken for an absent model. `TSV_NATIVE_PHENOTYPE` saves raw model compatibility, native priority score, model identifiers and scorer provenance; for TransD it also saves the raw triple score. TransD supplies a patient–gene score to each gene model. For native compatibility, raw TransD scores are min–max scaled over the genes passed to that prioritiser in the current analysis. Missing checkpoint genes receive the median covered-gene raw score before scaling; a case entity absent from the bundle is an error. A constant or entirely uncovered column maps to zero. Native scores consequently depend on the current gene pool.

Add `analysis.weightedVariants` and `TSV_TABLE3_WEIGHTED` for independent, distinct variant ranks. Its candidate membership is **exactly** the rows yielded by `GeneScoreRanker.rankedVariants()` for the same output settings as this run's `TSV_VARIANT`, collapsed by contig/start/ref/alt and unioning Entrez IDs. Output flags, native filters, inheritance, gene-score cutoffs and scorer choice can change that candidate pool. Selecting a learned scorer can therefore change the native gene scores and exported membership relative to the historical stock Exomiser CADD TSV used for Table 3. Parity requires comparing saved candidate identities before comparing component values or ranks. The weighted file labels this provenance and includes raw, imputed and normalized MS/GP, missing flags, weight and mid/strict variant ranks. The legacy variant and gene TSVs remain separate comparison outputs.

For INDIGENA weighted output, `genePhenotypes` is the benchmark's two-column `gene_phenotypes_mp.csv` with gene and MP annotation IRIs. These annotations are **pooled by gene**; no database-model maximum is used. Patient terms come from `patientHpo`, a controlled file with one HP ID or OBO IRI per line, if supplied. This permits exact benchmark term lists even when Exomiser's ontology gate revises the native sample HPO list. Without it, the weighted writer uses the parsed sample HPO IDs. Out-of-vocabulary patient and gene terms are excluded from BMA; every candidate gene with no usable pooled annotation retains an explicit zero phenotype row. MS is formatted to six decimals before variant combination, matching the benchmark score table. For TransD weighted output, raw checkpoint scores are used. Genes absent from the checkpoint have no score row and follow the configured MS missing policy at the variant level; explicit scores of zero remain zero.

`MAX_PATH` uses the legacy variant TSV's text value: `Float.toString(mostPathogenicScore().score())`, parsed back as a double, and a null predictor stays missing. The weighted TransD raw scores and pooled INDIGENA BMA scores are rounded to six decimals before combination, following the per-gene score table convention. Rounding acts on the exact Java binary score as Python formatting does; Java's BMA and TransD arithmetic may still produce a different final digit, so raw component agreement and ties must be measured case by case. TransD's raw triple score is higher when the association is stronger; a uniform positive scale factor such as the original EmbedPVP `/100` cancels under per-case min–max normalization, but rounding order may still matter and must be checked against frozen reference components. Missing predictor rows default to `ZERO`; missing variant MS rows default to `MEDIAN`. Both components are then min–max normalized over the distinct candidate variants and combined with `phenotypeWeight * MS + (1 - phenotypeWeight) * GP`. A constant component maps to zero. The selected weight is an input from validation, not chosen by this code. Native TransD imputes missing genes before gene-level normalization, while weighted mode imputes missing variant score rows after the gene maximum; the quantities differ. These weighted ranks do not claim numerical parity or a preset numerical tolerance until candidate identity, source values and term lists are independently checked against saved benchmark predictions.

See [INDIGENA example](src/main/resources/examples/learned-indigena-table3.yml) and [TransD example](src/main/resources/examples/learned-embedpvp-transd.yml). Use the selected embeddings/checkpoint, case terms, annotations and weight corresponding to the same experiment.
